# Командная разработка

## Начало работы

```sh
git clone https://github.com/m2k3d/phisicsPrj.git
cd phisicsPrj
git fetch origin
git switch -c codex/short-task-name origin/master
```

Для продолжения этапа 02 до слияния создайте ветку от `origin/review/blender-prototype`, когда она станет доступна. Если PR открыт из форка, получите ветку из этого форка и отметьте зависимость в своём PR. Согласуйте задачу и её границы в общем трекере. Одна задача ведётся в одной ветке или рабочем дереве.

Откройте соответствующее рабочее дерево как проект Codex или запустите `claude` из его корня. Codex читает [AGENTS.md](AGENTS.md), Claude Code импортирует его из [CLAUDE.md](CLAUDE.md). Передайте агенту цель, разрешённые для изменения файлы, зависимости от других задач и критерии проверки. Для работы со сценой настройте Blender MCP по [инструкции](docs/HANDOFF.md#blender-mcp). Для документации и чтения сцены из скрипта запуск MCP не требуется.

## Изменения и проверка

- До изменений проверьте `git status --short --branch`. Перед коммитом проверьте `git diff` и `git diff --cached`. Добавляйте файлы по именам и проверяйте, что в коммит не попали пользовательские конфиги, резервные копии, секреты и временные экспорты.
- Фиксируйте в коммите законченное изменение, в PR — команды, результаты проверок и оставшиеся вопросы. Для модели приложите контрольные кадры изменённых узлов. Для физики сверяйте результаты с [девятью эталонными сочетаниями](docs/physics.md#девять-сочетаний).
- При изменении сцены обновляйте координаты и результаты проверок в [отчёте о прототипе](docs/prototype.md) и, если затронуты имена или сборка узлов, [контракт GLB](docs/blender-glb.md). Отмечайте состояние этапов в [плане](plan.md). Внутренние ссылки оформляйте относительно файла документа.
- Изменения физических параметров и архитектуры предварительно согласуйте с командой. После согласования обновите [AGENTS.md](AGENTS.md) и связанные расчёты, спецификацию и критерии приёмки.

## Параллельная работа и файлы Blender

Два участника могут параллельно работать в отдельных ветках, если согласовали ответственность за файлы и общий контракт. Для общей схемы данных или узлов GLB заведите одну задачу с ответственным. Перед отправкой выполните `git fetch origin` и проверьте, как изменилась базовая ветка. Обсудите конфликт с владельцем затронутого участка и отразите принятое решение в PR.

У каждого `.blend` в конкретный момент один ответственный редактор. Перед правкой [prototype.blend](assets/blender/prototype.blend) отметьте в задаче, что берёте файл, и укажите исходный коммит. После изменения приложите скрипт или описание действий, новые контрольные кадры при визуальных изменениях и результат проверки GLB. Если появились две версии бинарника, выберите согласованную основу и перенесите изменения через Blender с повторной проверкой геометрии.

Текущие файлы хранятся в обычном Git. При заметном росте бинарников сначала проверьте лимиты и квоту Git LFS, затем согласуйте шаблоны отслеживания с командой. Внешние ресурсы добавляйте с проверенной лицензией и относительными путями либо упаковывайте в сцену, если это разрешает лицензия.

## Pull Request

1. Отправьте свою ветку командой `git push -u origin HEAD` при наличии доступа на запись. Если доступа нет, создайте форк на GitHub, добавьте его локально отдельным remote и отправьте ветку туда.
2. Откройте PR в `m2k3d/phisicsPrj:master`. Если задача зависит от ещё не принятого PR, укажите это в описании и согласуйте базу с проверяющим.
3. Укажите цель и состав изменений, результаты проверок, ссылки на документы и кадры, ограничения и вопросы для обсуждения. Пригласите ответственных за затронутые части.
4. Загрузите исправления после ревью в ту же ветку. Решение о слиянии принимает команда.
